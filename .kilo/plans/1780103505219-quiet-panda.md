# Plan: accélérer l’export MP4 incrusté avec une vraie chaîne GPU

## Objectif
Rendre l’export MP4 avec bande rythmo visible nettement plus rapide, sans mode sidecar, en évitant le piège actuel `CUDA decode -> hwdownload -> filtres CPU -> NVENC`.

Le résultat attendu reste un seul MP4 final avec :
- vidéo source en haut,
- bande rythmo incrustée en bas,
- audio source copié,
- FPS BR par défaut à 60,
- aucun fichier temporaire `br_temp.mp4`.

## Constats
- `src/video_export.rs` est déjà en single-pass : FFmpeg lit la source et reçoit les frames BR en rawvideo via stdin.
- Le chemin actuel tente CUDA avec `-hwaccel cuda -hwaccel_output_format cuda`, mais `fit_and_stack_filter(..., true)` commence par `hwdownload,format=nv12,` puis utilise `scale`, `pad`, `vstack`, donc les filtres lourds restent CPU.
- FFmpeg disponible sur cette machine expose :
  - encodeurs `h264_nvenc`, `hevc_nvenc`, `av1_nvenc`,
  - hwaccel `cuda`,
  - filtres `scale_cuda`, `overlay_cuda`, `hwupload_cuda`,
  - pas de `pad_cuda` ni `vstack_cuda`.
- On ne peut pas faire de stream copy pour la vidéo si la BR doit être visible : les pixels changent, donc réencodage obligatoire.
- On peut par contre garder `-c:a copy`.
- Le FPS par défaut BR est maintenant `DEFAULT_EXPORT_FPS = 60`.

## Stratégie
Remplacer le pseudo-chemin CUDA par un vrai graphe CUDA :
- décoder la source en CUDA,
- scaler la source avec `scale_cuda`,
- créer un canvas noir de taille finale,
- uploader le canvas noir en CUDA avec `hwupload_cuda`,
- uploader les frames BR raw en CUDA avec `hwupload_cuda`,
- composer avec deux `overlay_cuda` au lieu de `pad + vstack`,
- encoder directement avec `h264_nvenc` sans retour CPU.

Comme `pad_cuda` et `vstack_cuda` n’existent pas, l’empilement sera émulé ainsi :
- canvas noir final `out_w x (vid_h + br_h_even)`,
- overlay de la vidéo source centrée dans la zone haute `out_w x vid_h`,
- overlay de la BR à `y = vid_h`.

## Changements détaillés

### 1. Détection des capacités FFmpeg
Fichier : `src/video_export.rs`

Ajouter une détection de filtres :
```rust
fn has_filter(name: &str) -> bool
```
qui inspecte `ffmpeg -hide_banner -filters`.

Ajouter :
```rust
fn has_cuda_filter_graph() -> bool
```
qui exige :
- `has_nvenc()`,
- `has_cuda_hwaccel()`,
- `scale_cuda`,
- `overlay_cuda`,
- `hwupload_cuda`.

Important : ne plus tenter `-hwaccel cuda` si le graphe CUDA complet n’est pas disponible. Sinon, cela peut ralentir à cause du `hwdownload`.

### 2. Séparer les filtres CPU et CUDA
Fichier : `src/video_export.rs`

Garder un filtre CPU fallback proche de l’actuel :
```text
[0:v]scale=...:force_original_aspect_ratio=decrease,pad=...,setsar=1,format=yuv420p[v];
[1:v]format=yuv420p[br];
[v][br]vstack=inputs=2[out]
```

Ajouter un filtre CUDA :
```text
color=c=black:s=OUT_WxTOTAL_H:r=FPS:d=DURATION,format=nv12,hwupload_cuda[canvas];
[0:v]scale_cuda=w=OUT_W:h=VID_H:format=nv12:force_original_aspect_ratio=decrease:force_divisible_by=2:reset_sar=1[src];
[1:v]format=nv12,hwupload_cuda[br];
[canvas][src]overlay_cuda=x=(main_w-overlay_w)/2:y=(VID_H-overlay_h)/2[tmp];
[tmp][br]overlay_cuda=x=0:y=VID_H:shortest=1[out]
```

Notes :
- Le canvas remplace `pad` et `vstack`.
- La vidéo est centrée dans la zone haute.
- La BR est placée en bas.
- Toutes les frames du chemin CUDA doivent être `nv12` pour éviter conversions implicites coûteuses.

### 3. Utiliser NV12 pour la BR pipée
Fichier : `src/video_export.rs`

Remplacer ou compléter `rgba_to_yuv420p` par :
```rust
fn rgba_to_nv12(...)
```

Format attendu :
- plan Y complet,
- plan UV interleavé.

La taille reste `w * h * 3 / 2`, donc les buffers et capacités ne changent pas.

Changer l’entrée rawvideo FFmpeg de :
```text
-pix_fmt yuv420p
```
à :
```text
-pix_fmt nv12
```

Le fallback CPU convertira au besoin avec `[1:v]format=yuv420p[br]`.

### 4. Refactoriser `run_baked_single_pass`
Fichier : `src/video_export.rs`

Introduire une enum interne :
```rust
enum ExportPipeline {
    Cuda,
    Cpu,
}
```

Ou passer un bool explicite `use_cuda_graph`.

Comportement CUDA :
- ajouter `-hwaccel cuda -hwaccel_output_format cuda` avant l’input source,
- utiliser le filtre CUDA,
- ne pas ajouter `-pix_fmt yuv420p` à la sortie si cela force un download CPU,
- encoder avec `h264_nvenc`.

Comportement CPU :
- ne pas ajouter `-hwaccel cuda`,
- utiliser filtre CPU,
- garder `-pix_fmt yuv420p`,
- encoder avec `h264_nvenc` si disponible, sinon `libx264`.

En cas d’échec CUDA :
- logger l’erreur,
- supprimer l’output partiel,
- relancer tout le single-pass en CPU fallback,
- remettre la progression à `0.01`.

### 5. Presets encodeur orientés vitesse
Fichier : `src/video_export.rs`

Pour NVENC, utiliser un preset vraiment performance :
```text
-c:v h264_nvenc -preset p2 -rc constqp -qp 20 -b:v 0
```

Option alternative si besoin de qualité plus stable :
```text
-preset p4 -tune hq
```

Mais pour la demande actuelle “dans la vidéo et ultra rapide”, choisir `p2` par défaut.

Pour fallback CPU :
```text
-c:v libx264 -preset ultrafast -crf 20
```

Garder :
```text
-c:a copy
-shortest
-progress pipe:1
-nostats
```

### 6. Progression et deadlocks
Fichier : `src/video_export.rs`

Conserver les points importants déjà en place :
- stdin FFmpeg pour BR,
- stdout `-progress pipe:1` drainé dans un thread,
- stderr drainé dans un thread,
- fermeture explicite de stdin après écriture des frames,
- progression writer `0.01 -> 0.985`, puis `0.99`, puis `1.0`.

Ne pas lire stdout sur le même thread que l’écriture stdin.

### 7. UI
Aucun nouveau mode d’export.

À conserver :
- modal simple,
- FPS BR par défaut à `60`,
- pas de sidecar,
- résolution et zoom BR continuent à s’appliquer au MP4 incrusté.

### 8. Validation
Exécuter :
```text
cargo fmt
cargo check
```

Après `cargo fmt`, vérifier et restaurer si nécessaire le diff parasite connu dans :
```text
src/rythmo_cpu_renderer.rs
```

Tests manuels recommandés :
- exporter un petit MP4 et vérifier que la BR est visible en bas,
- vérifier que l’audio est présent,
- vérifier qu’aucun `temp/br_temp.mp4` n’est créé,
- surveiller Windows Task Manager onglets `Video Encode` / `Video Decode`, pas seulement `3D`,
- vérifier logs : le chemin CUDA doit annoncer `scale_cuda/overlay_cuda`, pas `hwdownload`.

## Limites assumées
- L’export ne peut pas être aussi rapide qu’un stream copy, car incruster la BR modifie les pixels.
- La BR est encore produite par l’app puis envoyée à FFmpeg par pipe. Un export 100% GPU nécessiterait un partage direct texture WGPU/CUDA ou un autre chemin d’encodage, ce qui est une refonte bien plus lourde.
- Le gain principal attendu vient de l’élimination des allers-retours source CPU/GPU et du remplacement de `scale/pad/vstack` CPU par `scale_cuda + overlay_cuda`.
