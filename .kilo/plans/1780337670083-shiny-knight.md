# Plan: Optimiser fortement le rendu des images et l'export MP4

## Contexte observe
- Le pipeline actuel utilise deja `h264_nvenc`, `scale_cuda`, `overlay_cuda` et `hwupload_cuda` quand ffmpeg les expose.
- Sur cette machine, ffmpeg expose bien `cuda`, `d3d11va`, `d3d12va`, `h264_nvenc`, `scale_cuda`, `overlay_cuda` et `hwupload_cuda`.
- Le gros goulot restant n'est pas le scale de la video source: il est dans la BR rendue par WGPU puis relue sur CPU.
- Aujourd'hui, la BR suit ce trajet: WGPU RGBA -> `copy_texture_to_buffer` -> `map_async` CPU -> copie RGBA dans un `Vec` -> conversion CPU RGBA vers NV12 -> ecriture `pipe:0` -> ffmpeg `hwupload_cuda` -> `overlay_cuda` -> NVENC.
- Les icones comediens sont decodees puis uploadees en texture WGPU avec cache, mais elles participent ensuite a ce chemin de readback CPU.
- `finish_render` retourne un `Vec<u8>` via `std::mem::take`, ce qui risque de recreer/reallouer le gros buffer RGBA a chaque frame.

## Objectif
Rendre l'export plus rapide en reduisant au maximum les copies CPU, les conversions CPU, les allocations par frame, les uploads repetes et les changements de bind group, tout en conservant un fallback robuste si CUDA ou WGPU ne sont pas disponibles.

## Strategie generale
1. Mesurer les temps par etape avant de changer l'architecture.
2. Appliquer les gains rapides peu risques: reuse de buffers, zero allocation par frame, compute shader WGPU pour RGBA -> NV12.
3. Ajouter un chemin ffmpeg CUDA plus agressif pour pousser les conversions BR dans CUDA quand c'est plus rapide.
4. Precomposer les images/textes statiques dans des atlas ou une couche timeline pour eviter de redessiner les memes icones/textures a chaque frame.
5. Garder le vrai zero-copy CUDA/DX12 comme chantier R&D separe, car ffmpeg CLI ne peut pas consommer directement une texture WGPU via `stdin`.

## Phase 1: instrumentation et benchmark
- Ajouter des timers dans `src/video_export.rs` autour de `write_br_frames`:
  - creation renderer GPU/CPU,
  - `submit_render`,
  - `finish_render`/readback,
  - conversion RGBA->NV12,
  - `writer.write_all`,
  - temps ffmpeg global.
- Ajouter des timers dans `src/rythmo_gpu_renderer.rs` pour:
  - upload initial des textes,
  - upload initial des icones,
  - nombre de textures creees,
  - nombre de bind groups/draw calls par frame,
  - taille lue depuis GPU par frame.
- Loguer un resume final: FPS rendu BR, FPS encode ffmpeg, millisecondes moyennes par etape, pipeline choisi.
- Faire les mesures sur au moins 3 cas:
  - projet court sans icones,
  - projet avec plusieurs comediens/icones,
  - projet long avec beaucoup de lignes.

## Phase 2: gains rapides sans changer le format ffmpeg
- Remplacer `GpuRenderer::finish_render(...) -> Vec<u8>` par une API du type `finish_render_into(&mut Vec<u8>)` pour reutiliser le meme buffer RGBA pendant tout l'export.
- Garder aussi une variante `finish_render_slice` ou `finish_render_with` si possible pour eviter les copies intermediaires.
- Reutiliser dans `GpuRenderer` les `Vec<QuadInstance>`, `Vec<IconInstance>` et `Vec<IconBatch>` comme champs du renderer au lieu de les recreer a chaque frame.
- Precalculer dans une structure `ExportScene` les elements qui ne dependent pas de la frame courante:
  - layout vertical,
  - `ppf`, `slot_h`, `badge_h`, `actor_icon_size`,
  - references de lignes visibles par slot,
  - association `actor_name -> actor asset/hash`,
  - largeur des badges,
  - segments syllabiques deja decoupes.
- Remplacer les recherches lineaires repetitives `project.find_voice_actor(actor_name)` par une map construite une fois par export.
- Coalescer les batches d'icones consecutifs ayant le meme hash pour reduire les draw calls quand c'est possible sans changer l'ordre visuel.

## Phase 3: conversion NV12 sur GPU WGPU
- Ajouter un compute shader WGPU `rgba_to_nv12.wgsl`.
- Rendre la BR en `Rgba8Unorm` comme aujourd'hui, puis lancer un pass compute qui ecrit directement le frame NV12 dans un buffer GPU.
- Lire seulement le buffer NV12 au lieu du RGBA:
  - taille lue: `width * br_h_even * 1.5` au lieu de `width * br_h * 4`,
  - suppression de `rgba_to_nv12` CPU dans le chemin GPU.
- Adapter `OffscreenTarget` pour posseder:
  - texture RGBA de rendu,
  - buffer GPU NV12/storage,
  - buffers staging NV12 double ou triple-buffered.
- Garder `rgba_to_nv12` CPU uniquement pour le fallback CPU ou pour debug.
- Ce changement est le meilleur compromis court terme: il accelere les images/icones/textes sans dependre de CUDA, tout en gardant ffmpeg avec `-pix_fmt nv12` et `hwupload_cuda`.

## Phase 4: chemin CUDA BR en RGBA optionnel
- Ajouter un mode experimental ou la BR WGPU est envoyee a ffmpeg en `rgba` au lieu de `nv12`.
- Modifier le deuxieme input ffmpeg:
  - `-f rawvideo -pix_fmt rgba -s {out_w}x{br_h_even} -r {fps} -i pipe:0`.
- Ajouter un filtre CUDA dedie:
  - `[1:v]format=rgba,hwupload_cuda,scale_cuda=w={out_w}:h={br_h_even}:format=nv12:passthrough=0[br]`
  - puis overlay avec `[tmp][br]overlay_cuda=...`.
- Ajouter un probe au demarrage d'export pour tester ce graphe sur 1 frame synthetique, car selon les builds ffmpeg `scale_cuda` peut refuser certains formats RGBA.
- Comparer ce mode au compute WGPU NV12:
  - si le pipe RGBA plus gros est compense par la conversion CUDA, l'utiliser,
  - sinon garder le mode WGPU compute NV12 comme mode par defaut.
- Nommer clairement les pipelines dans les logs: `GPU WGPU->NV12`, `GPU WGPU->RGBA->CUDA`, `CPU fallback`.

## Phase 5: atlas GPU pour icones et textes
- Construire un atlas de textures export avant la boucle de frames:
  - toutes les icones comediens decodees,
  - fallback initials/textes comediens,
  - noms de personnages,
  - notes,
  - tuiles de texte rythmo deja rasterisees.
- Remplacer les textures/bind groups par element par un ou quelques atlas:
  - un bind group pour l'atlas principal,
  - chaque `IconInstance` porte un `uv_rect` dans l'atlas,
  - reduction massive des `set_bind_group` et draw calls.
- Conserver une limite memoire et une eviction simple si l'atlas devient trop grand.
- Pour les textes rythmo tres longs, garder le tiling actuel mais inserer les tuiles dans l'atlas.
- Precharger l'atlas avant de lancer ffmpeg afin d'eviter les stalls d'upload pendant les premieres frames.

## Phase 6: couche timeline statique pour eviter de tout redessiner
- Introduire une couche `TimelineLayer` rendue une fois par export ou par chunks horizontaux.
- Cette couche contient les elements statiques en coordonnees monde:
  - badges,
  - icones comediens,
  - textes de ligne,
  - notes,
  - marqueurs qui bougent avec la timeline.
- A chaque frame, le renderer ne fait plus que:
  - sampler la fenetre visible de la couche timeline,
  - dessiner le fond,
  - dessiner le playhead,
  - dessiner les ticks dynamiques du ruler.
- Pour les videos longues, utiliser des chunks de timeline plutot qu'une texture geante:
  - largeur chunk configurable, par exemple 8192 ou 16384 px,
  - cache LRU de quelques chunks autour de la frame courante,
  - prefetch du prochain chunk pendant que ffmpeg encode.
- C'est probablement le plus gros gain sur les projets avec beaucoup de lignes/icones, car les images/textes ne sont plus re-emis et re-batches a chaque frame.

## Phase 7: ffmpeg CUDA graph plus propre
- Remplacer le graphe CUDA actuel par une version plus explicite:
  - `-init_hw_device cuda=cuda:0`,
  - `-filter_hw_device cuda`,
  - `-hwaccel cuda`,
  - `-hwaccel_output_format cuda`,
  - eventuellement `-extra_hw_frames` pour eviter les stalls.
- Garder le canvas dans CUDA:
  - `color=...,format=nv12,hwupload_cuda[canvas]` reste acceptable,
  - ou tester `nullsrc`/`scale_cuda` selon ce qui est plus stable.
- Ajouter `scale_cuda=interp_algo=bilinear|lanczos` configurable si la qualite/perf doit varier.
- Ne pas utiliser `vstack` dans le chemin CUDA, car il n'y a pas de `vstack_cuda`; garder la composition via canvas + `overlay_cuda`.

## Phase 8: vrai zero-copy CUDA/DX12, seulement si necessaire
- Le vrai full GPU voudrait eviter completement `pipe:0` et le readback CPU.
- Avec ffmpeg CLI, ce n'est pas realiste directement: `stdin` transporte des bytes CPU, pas des textures WGPU.
- Options possibles mais beaucoup plus risquees:
  - passer de ffmpeg CLI a libavcodec/libavfilter in-process avec `AVHWFramesContext`,
  - utiliser l'interop DX12/D3D11/CUDA avec shared handles,
  - exposer les handles natifs WGPU via `wgpu-hal`, ce qui est instable et backend-specific,
  - ou reimplementer le renderer BR directement en CUDA puis encoder via NVENC/libavcodec.
- Cette phase doit rester separee tant que les phases 2 a 6 n'ont pas ete mesurees, car elle augmente fortement la complexite et le risque de bugs GPU/driver.

## Validation
- `cargo fmt -- --check`.
- `cargo check`.
- `cargo test`.
- Export manuel avec pipeline CUDA disponible:
  - verifier log `scale_cuda + overlay_cuda`,
  - verifier affichage `Export GPU`,
  - verifier que les icones restent visibles et bien positionnees,
  - verifier que l'output audio/video reste synchronise.
- Export manuel en forcant l'indisponibilite GPU:
  - verifier fallback CPU,
  - verifier affichage `Export CPU`.
- Comparer les temps avant/apres avec les memes projets:
  - temps total export,
  - FPS BR rendu,
  - temps moyen readback,
  - temps moyen conversion,
  - debit pipe ffmpeg.

## Ordre recommande d'implementation
1. Instrumentation benchmark.
2. Reuse des buffers et suppression des allocations par frame.
3. Compute shader WGPU RGBA -> NV12.
4. Probe et chemin experimental RGBA -> `hwupload_cuda` -> `scale_cuda`.
5. Precompute `ExportScene` et map acteurs.
6. Atlas textures pour icones/textes.
7. Couche timeline statique chunked.
8. Etude zero-copy libav/DX12/CUDA seulement si les gains precedents ne suffisent pas.

## Risques et decisions
- Le chemin CUDA RGBA depend fortement du build ffmpeg; il doit etre detecte par probe et non suppose disponible.
- La conversion NV12 compute WGPU est moins spectaculaire que le zero-copy, mais beaucoup plus fiable et devrait deja supprimer un gros cout CPU.
- L'atlas et la couche timeline doivent respecter l'ordre visuel existant; il faudra separer les layers si certains elements peuvent se chevaucher.
- Les optimisations doivent garder les statuts UI `Export GPU`/`Export CPU` alignes avec le backend reel.
