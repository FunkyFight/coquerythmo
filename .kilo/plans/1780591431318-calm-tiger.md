# Plan: Optimiser le rendu UI karaoke long

## Constat
- La UI refait des scans complets de `project.lines()` dans des helpers appelés pour chaque ligne rendue.
- Avec un karaoke long, le rendu devient au minimum `O(n²)` par frame, et parfois pire pour `karaoke_stack_row` car il remonte la chaîne d’îlot en rescannant le projet.
- Les layouts de tracks sont aussi recalculés pour chaque `line_rect`, et chaque recalcul rescane le projet via `track_has_karaoke`.
- Le cache GPU du texte limite déjà la rerasterisation, donc la priorité est de supprimer les rescans et mesures répétées côté UI.

## Objectif
Rendre la preview interactive/studio scalable pour des karaokés de plusieurs minutes en gardant le comportement actuel:
- seules les tracks karaoke ont un corps double,
- alternance haut/bas par îlot,
- une ligne normale coupe l’îlot,
- labels personnage au début d’un îlot ou changement de personnage,
- preview UI cohérente avec export.

## Changements Prévus
1. Ajouter un contexte de layout UI calculé une fois par frame
- Créer une petite structure locale dans `src/ui/rythmo.rs`, par exemple `EditorLayoutCtx`, contenant:
  - `normal_body_h`,
  - `track_layouts`,
  - lookup par track index pour `y_base` et `body_rect`.
- Remplacer dans les chemins chauds les appels répétés à:
  - `editor_track_layouts`,
  - `editor_track_y_base`,
  - `editor_track_body_rect`,
  - `line_rect_with_karaoke_preview`,
  par des variantes qui prennent `&EditorLayoutCtx`.
- Garder les anciennes fonctions comme wrappers si elles sont utiles aux tests ou aux chemins non critiques.

2. Pré-calculer l’état karaoke par ligne en `O(n log n)` ou `O(n)` par frame
- Créer une structure locale, par exemple `KaraokeUiIndex`, construite une fois depuis `project.lines()` et `max_gap_frames`.
- Grouper les lignes par `track_index_for_y_slot`, trier chaque groupe par `(start_frame, id)` si nécessaire.
- Pour chaque ligne, calculer et stocker par `line.id`:
  - `previous_adjacent_karaoke_id`,
  - `stack_row`,
  - `label_visible`,
  - `prestart_scroll_visible`,
  - `upcoming_stack_visible` selon `current_frame`,
  - éventuellement `island_index` si utile aux tests/debug.
- Respecter la règle actuelle: seule la ligne immédiatement précédente sur la même track compte; si elle est normale, elle coupe l’îlot.

3. Utiliser ces contextes dans les rendus UI
- Dans `render_lines`, construire `EditorLayoutCtx` et `KaraokeUiIndex` une seule fois.
- Remplacer les appels chauds à:
  - `karaoke_prestart_scroll_visible`,
  - `karaoke_upcoming_stack_visible`,
  - `karaoke_stack_row`,
  - `karaoke_character_label_visible`,
  par des lectures `O(1)` dans l’index.
- Faire la même chose dans `render_studio_rythmo` pour éviter les rescans studio.
- Dans `render_rythmo_base` / playhead skip ranges, utiliser aussi un index local ou une fonction indexée pour éviter les calculs récursifs.

4. Réduire les mesures texte répétées
- Ajouter un petit cache de largeur karaoke UI, idéalement dans `RythmoState` ou dans un cache renderer existant:
  - clé: `(line.id, text hash/len, font_size bits)`,
  - valeur: largeur naturelle mesurée.
- Remplacer `karaoke_ui_text_width(&line.text)` dans les chemins actifs/upcoming par une lecture de cache avec recalcul uniquement si texte ou taille de police changent.
- Garder le fallback char-count actuel si la mesure échoue.

5. Optimiser sans changer la sémantique export
- Ne pas toucher au calcul export CPU/GPU sauf si une duplication évidente peut être partagée sans risque.
- Priorité à l’UI interactive et studio, là où le problème se manifeste pendant la lecture.

## Tests À Ajouter/Adapter
- Tests unitaires sur `KaraokeUiIndex`:
  - alternance haut/bas identique aux tests existants,
  - ligne normale qui coupe l’îlot,
  - label visible au début ou changement personnage,
  - même comportement avec `y_slot` légèrement drifté mais même track quantifiée.
- Test layout UI:
  - `EditorLayoutCtx` donne les mêmes rects que les wrappers existants.
- Garder et faire passer les tests existants:
  - `cargo test karaoke`,
  - `cargo test`.

## Validation Manuelle Recommandée
- Ouvrir un projet karaoke long (~10 min) et vérifier que la lecture UI reste fluide.
- Vérifier une track normale + une track karaoke: la normale reste mono-ligne.
- Vérifier une séquence karaoke longue: alternance haut/bas et labels personnage inchangés.
- Vérifier studio preview sur un projet long.

## Risques
- Les fonctions de géométrie sont beaucoup appelées depuis render, hit-testing et édition; il faut migrer les chemins chauds sans casser les wrappers existants.
- Un cache de largeur texte doit être invalidé sur changement de texte et taille de police, sinon la position centrée peut devenir fausse.
- Si on trie par frame pour l’index, il faut conserver le tie-breaker par `id` pour rester déterministe.
